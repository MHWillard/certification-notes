BUILD TABLES
tables: organizing data into rows and columns that represent entities and their attributes.
In relational systems, tables define the structure for storing transactional data, enforce relationships through foreign keys, and provide the foundation for queries and reporting.

fact tables storing measurable events
dimension tables providing context for analysis.
data types, column sizing, constraints, and relationships—directly impact storage efficiency, query performance, data integrity, and scalability

data type determines precision, storage space, and size for query speed so choose right the first time

Table size affects backup and restore times, index rebuild durations, and query performance: also cloud storage costs

Use appropriate data types - Smaller data types reduce storage and improve performance
Consider table size early - Estimate row size and total table size to plan storage and indexing
Implement meaningful constraints - Ensure data quality at the database level
Plan for growth - Design tables to handle future data volume
Index strategically - Index columns used in WHERE, JOIN, and ORDER BY clauses
Choose columnstore for analytics - Use columnstore indexes for large tables with analytical queries
Normalize when appropriate - Balance normalization with query performance needs
Monitor row and page compression - Enable compression for large tables to save storage

OPTIMIZE INDEXES
Indexes are data structures that accelerate data retrieval by creating optimized lookup paths to table rows.
An index works like a book's index: instead of reading every page to find an article, you consult the index to jump directly to relevant pages

Designing efficient indexes is key to achieving good database and application performance. A lack of indexes, over-indexing, or poorly designed indexes are top sources of database performance problems.

Rowstore indexes organize data in row format, storing all columns of a row together on the same page, which makes them optimal for transactional workloads that retrieve complete records or perform frequent updates.

A clustered index sorts and stores the data rows in the table based on their key values. These key values are the columns included in the index definition. There can be only one clustered index per table, because the data rows themselves can be stored in only one order.
Clustered indexes are best when you need efficient range queries, stable and narrow keys, or a natural sort order such as identity columns or date fields because they define the physical row order and optimize scans over ordered data.

A nonclustered index has a structure separate from the data rows. A nonclustered index contains the nonclustered index key values and each key value entry has a pointer to the data row that contains the key value. You can create multiple nonclustered indexes on a table or indexed view.
Nonclustered indexes are ideal when you need fast lookups for specific predicates, joins, or sorting patterns that don't align with the clustered key, or when you want to cover a query by including extra columns to avoid key lookups.

columnstore: storing data column-by-column, reading only the columns required for your query, for analytics

A columnstore index organizes data into rowgroups
Within each rowgroup, the engine stores each column separately as a column segment

When you insert data, small batches first go to a deltastore—a temporary rowstore structure using a B+ tree index.
Once a delta rowgroup accumulates enough rows (at least 102,400), a background process called the tuple-mover compresses it into the columnstore.

A Clustered Columnstore Index (CCI) is a type of columnstore index that becomes the primary storage structure for the entire table, replacing any existing clustered rowstore index.
Unlike a nonclustered columnstore index (NCCI), which creates a secondary columnar copy alongside the rowstore table, a CCI stores all table data exclusively in columnar format.

A Nonclustered Columnstore Index (NCCI) creates a separate columnar copy of selected columns alongside the existing rowstore table, allowing the same table to serve both transactional and analytical workloads efficiently.

You can monitor the health and performance of your columnstore indexes by querying the sys.dm_db_column_store_row_group_physical_stats dynamic management view.

TABLE TYPES
SQL Server support specialized table types designed for specific scenarios and workloads beyond standard disk-based tables.

In-memory optimized tables
Traditional disk-based tables incur latency from disk I/O, even with caching.
In-memory tables eliminate this by keeping data entirely in RAM with lock-free, optimistic concurrency.
- Good for: session state storage, real-time analytics, high-frequency OLTP, caching layer, staging tables

Temporal tables automatically track the complete history of data changes. When you update or delete a row, SQL Server automatically stores the previous version in a linked history table with timestamps showing when that version was valid.
- good for: compliance, auditing, troubleshooting, trend analysis, data recovery, slowly changing dimensions

External tables enable data virtualization to query data where it lives without moving it, saving storage costs and ETL complexity.
- good for: data lake integration, data exploration, cost optimization, federated queries, archival storage

Ledger tables use cryptographic verification inspired by blockchain technology to create tamper-evident records that can be independently verified
- good for: financial transactions, supply chain, legal records, healthcare, government
- Two types:
1. Updatable ledger tables allow INSERT, UPDATE, and DELETE operations while tracking all changes cryptographically. The system automatically stores previous versions in a history table, similar to temporal tables, but with the added benefit of tamper-proof verification. 
2. Append-only ledger tables only allow INSERT operations, creating truly immutable records for scenarios requiring absolute data integrity.

Graph tables simplify relationship modeling but require learning new syntax. They provide intuitive modeling of connected data, simpler queries for relationship traversal, and better performance for multi-hop queries
-Two types:
1. Node tables store entities and automatically include a hidden $node_id column that uniquely identifies each node. 
2. Edge tables store relationships between nodes and include hidden columns $edge_id, $from_id, and $to_id to maintain connections.

CONSTRAINTS
SQL constraints are rules for data in a table.
Constraints are used to prevent insertion of invalid data in a table, and ensures the accuracy and reliability of the data in the table. If there is any violation between the constraint and the data action, the action is aborted

Primary key constraints: When you specify a primary key constraint, the Database Engine automatically creates a unique index for the primary key columns. A table can contain only one primary key constraint, and all columns defined within a primary key constraint must be defined as NOT NULL.

A foreign key constraint prevents changes to data in the primary key table if those changes invalidate the link to data in the foreign key table.

Unique constraints ensure no duplicate values are entered in specific columns that don't participate in a primary key.

Check constraints enforce domain integrity by limiting the values accepted by one or more columns.

Default constraints provide default values when no value is specified during INSERT operations

A sequence object is a user-defined schema-bound object that generates a sequence of numeric values according to the specification with which the sequence was created.
- good for needed number series and sorted sequence values

Unlike identity columns, sequence values aren't automatically protected after insertion into a table. Also, uniqueness isn't automatically enforced for sequence values.

PARTITIONING TABLES
Table partitioning divides large tables into smaller, more manageable pieces (partitions) while keeping them as a single logical table. Your application sees one table, but the database engine manages multiple physical segments that can be independently maintained, archived, or queried.

plan and do it right the first time otherwise you will seriously fuck things up

Partitioning involves several key components: 
-a partition function that defines how data is divided
-a partition scheme that maps partitions to filegroups
-partitioning column that determines which partition each row belongs to.

benefits:
-queries filter by partition key access only relevant partitions
-parallel processing where multiple partitions are processed simultaneously across CPU cores
-aster statistics calculated per partition instead of the entire table
-and index seeks where smaller partitions mean shallower B-trees.

operational benefits:
granular maintenance where you rebuild indexes on the current partition while older partitions remain online
-fast archival by switching old partitions to archive tables in seconds through metadata operations
-improved availability from maintaining partitions independently
-tiered storage by moving older partitions to cheaper, slower storage.

partition key selection criteria:
-Query patterns: 80%+ of queries filter by this column
-Data distribution: Even distribution across partitions (no single partition with 90% of data)
-Maintenance alignment: Matches archival/purge patterns (date columns for time-based archival)
-Stability: Value doesn't change after INSERT (avoid partitioning on updateable columns)

Range partitioning divides data based on value ranges—most commonly dates.
ideal for time-series data, sequential data, numeric ranges

You can use RANGE partitioning with string or categorical values like regions. The partition function places values based on sort order.

When you partition a table, indexes can be aligned or nonaligned. 
- Aligned indexes use the same partition function as the table. Each index partition matches a table partition
- Nonaligned indexes use different partitioning or no partitioning. They can't use partition switching and aren't supported on tables with more than 1,000 partitions.

partition maintenance:
querying partition metadata, adding new partitions as data grows, and removing old partitions during archival. 

partitioning best practices:
- Align indexes with table partitions
- Monitor data distribution
- Automate partition management
- Avoid over-partitioning: too many partitions create overhead
- Include partition key in primary key

VIEWS
A view is a virtual table based on a SELECT statement. Unlike physical tables, views don't store data themselves. Instead, they retrieve data from underlying tables each time you query them.
You can also create views with calculated columns. 

Specify column names explicitly instead of using SELECT *. Explicit columns make views more maintainable and prevent unexpected results when underlying tables change.
Use the WITH CHECK OPTION clause when views will handle data modifications. This option ensures that INSERT and UPDATE statements through the view only affect rows visible in the view.

Keep view definitions focused on a specific purpose.
Use views to simplify complex queries that multiple applications or users need to execute.
Consider views when you need to restrict data access at the column or row level.

STORED PROCEDURES
A stored procedure is a compiled collection of T-SQL statements that SQL Server stores and executes as a single unit.
With stored procedures, the execution plan is cached after the first run

Parameters: use the @ symbol followed by a parameter name and data type.
@StartDate datetime = NULL

Output parameters let you return values to the calling application. You define them using the OUTPUT keyword:
@TotalAmount decimal(10,2) OUTPUT

Try catch error handling:
Always check @@TRANCOUNT before rolling back transactions in the CATCH block. This prevents errors if the transaction already completed or was never started.

Practices:
- Use schema-qualified names for all objects: dbo.Orders
- Implement parameter validation at the start of your procedure.
- Use meaningful names that describe what the procedure does.

SCALAR FUNCTIONS
Scalar functions: encapsulate reusable logic and return a single value.
A scalar function accepts zero or more parameters and returns a single value of a specified data type. Unlike stored procedures, scalar functions can be embedded directly in SQL expressions wherever you would use a column or variable.

First, keep your scalar functions deterministic whenever possible. A deterministic function always returns the same result given the same input parameters.
Scalar functions shouldn't modify database state or have dependencies on external resources.
When you use a scalar function in a WHERE clause or SELECT list with large tables, SQL Server may execute the function for every row. This can significantly impact query performance. For such scenarios, consider inline table-valued functions as an alternative.

TABLE-VALUED FUNCTIONS
Table-valued functions let you encapsulate complex query logic into reusable components that return result sets (tables). You can call these functions directly in queries, just like tables or views

- Inline table-valued function: Contains a single SELECT statement and returns results directly. With inline functions, you don't define the table structure—SQL Server infers it from your SELECT statement.
- Multi-statement table-valued function: Uses a BEGIN...END block and explicitly declares the structure of the returned table. This type gives you more control when you need to execute multiple statements, perform complex calculations, or build the result set iteratively. 

CREATE FUNCTION dbo.GetCustomerOrders
(
    @CustomerID INT
)
RETURNS TABLE
AS
RETURN
(
    SELECT OrderID, OrderDate, TotalAmount, Status FROM Sales.Orders WHERE CustomerID = @CustomerID
);

The CROSS APPLY operator calls the function for each row from the Customers table, though in this example, the function parameters are constants

TRIGGERS
Triggers are special stored procedures that automatically execute when specific events occur in your database. 

SQL Server supports two main categories of triggers: DML (Data Manipulation Language) triggers and DDL (Data Definition Language) triggers. 
DML triggers respond to changes in table data, while DDL triggers respond to schema changes like CREATE, ALTER, or DROP statements.

DML triggers monitor and respond to data changes in tables or views. You define them as either AFTER triggers or INSTEAD OF triggers.

- Keep your trigger logic focused and minimal. Execute only essential operations within the trigger body.
- Avoid recursive operations where a trigger modification causes the same trigger to fire again. Set the RECURSIVE_TRIGGERS database option
- Handle errors properly within triggers. If a trigger encounters an error and you don't handle it, SQL Server rolls back both the trigger and the original statement:

COMMON MISTAKES
- Using scalar functions in WHERE clauses on large tables— The function executes for every row, degrading performance. Consider inline table-valued functions or rewriting the logic.
- Creating triggers for logic that stored procedures handle better— Triggers execute implicitly and can be hard to debug. Use them only when automatic execution is essential.
- Building complex views that nest other views— Deeply nested views become difficult to optimize and maintain. Keep view definitions focused and shallow.
- Choosing stored procedures when a function would integrate better— If you need the result in a SELECT statement, a function provides cleaner syntax than EXEC with temp tables.

COMMON TABLE EXPRESSIONS
Common Table Expressions (CTEs) provide a way to define temporary named result sets that exist only during a single query
A Common Table Expression is defined using the WITH clause, followed by the CTE name, an optional column list, and a query that defines the result set.

Advantages: readability, can self-reference itself, multiple references, modular

Nonrecursive CTEs define a result set based on a straightforward query that doesn't reference itself.

Recursive CTEs reference themselves to process hierarchical or graph-like data structures. 
A recursive CTE consists of two parts: an anchor member that provides the initial result set, and a recursive member that references the CTE to build upon previous results.
Recursive CTEs excel at generating sequences of numbers or dates without requiring a physical numbers table.

WINDOW FUNCTIONS FOR ANALYTICS
Traditional aggregate functions collapse rows into groups, losing row-level information. Window functions solve this challenge by performing calculations across a set of rows related to the current row, without collapsing the result set.

Window functions calculate values across a "window" of rows defined by the OVER clause. Unlike regular aggregate functions, window functions don't group rows into a single output row. Instead, they compute values across related rows while preserving all original rows in the result.


PROCESS JSON WITH BUILT-IN FUNCTIONS
JSON_VALUE() extracts a scalar value (string, number, boolean) from a JSON string:
    SELECT JSON_VALUE(@json, '$.customer.id') AS CustomerID
JSON_QUERY() extracts a JSON object or array (nonscalar values)
    SELECT JSON_QUERY(@json, '$.customer') AS CustomerObject
-JSON_QUERY() preserves the JSON structure, returning objects and arrays as valid JSON strings

OPENJSON is a table-valued function that transforms JSON data into a relational rowset. 
--OPENJSON returns three columns: key (the array index or property name), value (the JSON content), and type (a number indicating the JSON data type: 0=null, 1=string, 2=number, 3=boolean, 4=array, 5=object).

JSON_OBJECT() creates a JSON object from key-value pairs.
JSON_ARRAY() creates a JSON array from values.
JSON_ARRAYAGG aggregates values from multiple rows into a single JSON array. 
    SELECT JSON_ARRAYAGG(soh.SalesOrderID) AS OrderIds

Validating and checking JSON:
ISJSON validates whether a string contains valid JSON.
JSON_PATH_EXISTS checks whether a specific path exists in a JSON document

Computed columns let you extract JSON values once and store them in a queryable format that supports indexing.

For comprehensive JSON output from queries, use FOR JSON PATH or FOR JSON AUTO

FUZZY STRING FUNCTIONS
 Fuzzy string matching functions help you find records that are similar but not identical, because data doesn't always perfectly match
* Edit distance (Levenshtein distance) counts the minimum number of single-character operations (insertions, deletions, substitutions) needed to transform one string into another.
* Similarity scores express the relationship between strings as a percentage or ratio, where higher values indicate greater similarity.

The EDIT_DISTANCE function returns the Levenshtein distance between two strings, which is the minimum number of edits required to transform one string into the other.
EDIT_DISTANCE_SIMILARITY returns a normalized similarity score between 0 and 100, where 100 represents identical strings.

The Jaro-Winkler algorithm is designed for comparing names and short strings. It gives higher scores to strings that match from the beginning.
The Jaro-Winkler score ranges from 0 to 1, where 1 indicates identical strings.

The key to efficient fuzzy matching is reducing the candidate set before applying the expensive fuzzy functions. 

GRAPH QUERIES
Graph data:
* Nodes (boxes) represent entities like people and products
* Edges (arrows) represent relationships between nodes. Arrow direction indicates the relationship direction (Alice knows Bob, not necessarily Bob knows Alice).

Graph queries with dedicated node/edge tables
match patterns with syntax instead of joins

Node tables store entities in your graph. Create them using CREATE TABLE with the AS NODE clause
Edge tables represent relationships between nodes. Create them using CREATE TABLE with the AS EDGE clause:

The MATCH clause uses a pattern syntax to specify the relationships you want to find. 
    SELECT a FROM b WHERE MATCH(Employee-(r)->Manager);
    [(Node1)-(Edge)->(Node2)]
    chain: WHERE MATCH(Person1-(k1)->Person2-(k2)->Person3)
* arrows can go either way

You can use SHORTEST_PATH to find the shortest connection across a variable number of relationships.
    WHERE MATCH(SHORTEST_PATH(StartPerson(-(k)->ReachablePerson){1,3}))

CORRELATED SUBQUERIES
Correlated queries are subqueries that reference columns from the outer query, creating a dependency that causes the subquery to execute once for each row processed by the outer query.
--kind of like a nested loop

Correlated subqueries in the WHERE clause: each row is evaluated against a dynamically calculated value based on that row's attributes.

The EXISTS operator combined with a correlated subquery tests whether any matching rows exist in a related table, returning a simple true or false result.

Correlated subqueries in the SELECT clause calculate a separate value for each row in your result set.

Correlated subqueries can access values from previous or subsequent rows based on ordering criteria

Good correlated subquery performance:
-check execution plans
-test on realistic data volumes
-use indexes accordingly

MODEL CONTEXT PROTOCOL OPTIONS
Selecting the right model and configuring Model Context Protocol (MCP) tools significantly improves the relevance and accuracy of AI suggestions for your database work.

Model Context Protocol (MCP) is an open standard that allows AI assistants to connect directly to external data sources and tools. Instead of the AI assistant only seeing the code in your editor, MCP enables it to query your actual database schema, sample data, and metadata in real time.

MCP follows a client-server architecture:

MCP Host: Your AI environment (GitHub Copilot, Claude, etc.)
MCP Client: The protocol client that connects to MCP servers
MCP Server: A service that exposes specific data sources or tools

SQL MCP Server: Connects to SQL Server and Azure SQL databases using Microsoft's open-source solution built on Data API builder.

Microsoft Fabric MCP Server: Connects to Fabric data agents as MCP servers, enabling AI assistants to query lakehouses, warehouses, and SQL databases within Fabric workspaces.

Azure MCP Server: Provides broader Azure resource integration, including database services.

best practices:
-start with default model/MCP setting then adjust
-match models to right types of tasks
-set up MCP connections with least-privilege access
-test confiugurations and verify suggestions
